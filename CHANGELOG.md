## [Unreleased]

- **The console deploys itself to a GKE cluster on every push to `main`, and a rollout is not green until it has actually talked to the platform** (2026-08-08): the console had a published image and no deployment — `docker run` in a README is not an environment somebody can open. It now has one: a single staging cluster (`map-staging`, `us-central1-a`) in the same namespace as the platform it manages, so the console reaches the control plane over cluster DNS and **the management key never leaves the cluster**. [.github/workflows/deploy.yml](./.github/workflows/deploy.yml) builds an amd64 image tagged with the commit sha — amd64 alone is the right answer here, unlike the release workflow's multi-arch build, because the target is one cluster of x86 nodes rather than whoever pulls — pushes it to Artifact Registry, and applies the two objects in [deploy/k8s/](./deploy/k8s/). **No credential is stored in this repository:** the job mints an OIDC token, Workload Identity Federation exchanges it for an impersonation of a deploy identity that can push images, drive the cluster, and read secrets and nothing else, and both runtime credentials are read from Secret Manager inside the job — `controlplane-api-key`, the same value the platform chart installs as `controlplane.apiKey`, and `console-password`. Rotating either means adding a Secret Manager version, not editing settings on GitHub. A rotation reaches the pod, too: the pod template carries a `console-secrets/checksum` annotation over the two payloads — the same device the platform chart uses — so a `workflow_dispatch` on an unchanged `main` is a new revision rather than a byte-identical apply that reports success, rolls nothing, and leaves the pod on the old credentials. CD deliberately runs no Terraform: the cluster, the registry, the federation pool and the secrets stay human-driven and interactive, and this pipeline owns four verbs — build, push, deploy, smoke. The last one is the point, and it asks two questions from two places. **Can this revision serve?** `kubectl rollout status` proves only that a container starts and answers a probe that touches no network, which a revision with a wrong key passes; so the job runs the deep health check with `kubectl exec` against the pod carrying the image it just pushed, over loopback, logging in with the `CONSOLE_PASSWORD` the container already holds — both variables set, and the platform accepting the key. **Is the public address gated?** From outside, it requires the shallow check to answer 200 (the load balancer routes, the pod serves), the body to report `login_gate: true`, and an anonymous `GET /` to come back 307 to `/login` — that last one being the only one of the three that is evidence, since "a non-empty password existed in Secret Manager at deploy time" is a different claim from "the pod on the internet is gated". It also refuses to deploy at all if `console-password` is empty, because this deployment is published on a bare public IP with **no domain and no TLS yet** (a deliberate, recorded limitation — an Ingress needs a hostname and cert-manager needs a domain, and there is neither), which makes an unset gate an open page in front of a full-power management key rather than the convenience it is on `localhost`. Documented end to end in [docs/deploy-gcp.md](./docs/deploy-gcp.md), including how to roll back — the image tag is the commit sha and is never reused, so every revision the cluster has run is still addressable.
- **A health endpoint, and the login gate no longer hides it** (2026-08-08): `GET /api/health` is the machine-readable answer to "can this revision work", and it has two depths because a probe and a deploy gate want different things — the shallow check reads configuration and touches no network, the deep one (`?deep=1`) also calls the platform with the management key. The readiness and liveness probes take the shallow one on purpose: a probe that failed during a platform outage would remove the console from service exactly when a console that can still render its own error is the more useful thing to have. Wiring the Kubernetes probes surfaced the half that would have made the whole pipeline unusable — `src/proxy.ts`'s matcher covered `/api/health`, so on a gated deployment the endpoint answered 401, which a readiness probe reads as an unhealthy container: the pod would never have become ready, `rollout status` would have timed out, and the smoke gate would have failed every rollout of the one deployment where the gate is **mandatory**. The route is now exempt from the matcher, and written for the anonymous caller that exemption creates: it names environment variables that are already public in `.env.example` and reports the platform's status code, carrying no URL and no key. **The deep depth gates itself instead.** Exempting the route made `?deep=1` an anonymous lever on a console published at a bare public IP — repeat it and you make the console spend the management key against the control plane on demand — so on a gated console that depth now requires the same session every page does, and answers the login gate's own 401 envelope without it. The deploy gate therefore runs it from inside the pod rather than over the public IP, logging in over loopback with the container's own copy of the password; what crosses the public address is the shallow check and the anonymous request that must be bounced. With `CONSOLE_PASSWORD` unset there is no gate to hold a session against and no console to protect, so the deep depth stays open, exactly as every other route does. Three of the route's twenty tests are `probe:` tests pinning the no-leak invariant: whatever the platform answers — a body echoing the key back, an HTML error page, a rejection whose message quotes the request headers — the serialized health body contains neither the key nor the base URL, and the upstream body is drained rather than left holding a connection.
