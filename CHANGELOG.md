# Changelog

Notable changes, newest first. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/); each entry is the one place a change's narrative is written.

This file holds the cycle in progress. **Released cycles live in [docs/changelog/](./docs/changelog/)**, one file per version — entries here are narrative paragraphs, and a single file accumulating them would make every reader pay for the whole project's history to see what changed this week.

## [Unreleased]

- **Two live specs stop asserting the platform's render and start asserting their own invariant** ([#66](https://github.com/OpenSDLC-Dev/managed-agent-console/issues/66), 2026-08-09): both pinned an agent's `tools` with `toEqual`, which made them fail against a platform carrying [#343](https://github.com/OpenSDLC-Dev/managed-agent-platform/pull/343) — **not a console regression**, and the distinction is the whole point. That change resolves toolsets **at render**: `configs` and `default_config` come back with every `enabled` and `permission_policy` concrete, while stored rows keep the client's own bytes. So the authored document and its echo are not the same document, and an exact-equality assertion against the echo pins whichever defaults the platform happened to spell out that week — it broke once and would break again the next time an implicit default became explicit, which is the console being **stricter than the wire** in the one place principle 4 forbids it. Each spec now asserts what it was actually written for. The round-trip spec: the compact shape survived a console save as **one** entry with `default_config.enabled` still `false` and an **empty** `configs` — the last part deliberately still exact, because a populated `configs` here _is_ the explosion into eight per-tool entries the test exists to catch, so relaxing that would have thrown the test away rather than fixed it. The starter-template spec: `bash` carries `permission_policy.type === "always_ask"`, the gate the template promises, and nothing about the fields the platform fills in around it. **Loosening a test is exactly where a fix can quietly delete the coverage it claims to preserve, so the new assertions were checked against real platform responses rather than reasoned about.** Both regressions were reproduced on a live stack and fed to the new predicates: an agent authored with all eight per-tool entries is **rejected** by the round-trip predicate, an agent whose `bash` is `always_allow` is **rejected** by the template predicate, and the two correct shapes pass — so the specs are looser about the render and no weaker about the defect. Verified by running the two specs against the local `deploy/compose` stack (both green in 9.3 s), which is also the only place they can be verified: the live tier is opt-in and never runs in CI.

- **Plan 06 is complete and archived: the refusal half of the gate is confirmed** (2026-08-09): the maintainer signed in with a Google account **outside** the Workspace and was refused, which was the last acceptance check the plan named and the one nobody could perform on the deployment's behalf — it needs a second account, and no amount of configuration reading substitutes for it. That matters more than a box being ticked, because **admission and refusal are separate claims** and only the first had been demonstrated: an account inside the domain reaching `/agents` proves the door opens, and proves nothing whatsoever about whom it opens for. A gate that admits everyone passes that test perfectly. The specific risk this closes is the one the plan chose `domain:` to avoid — every application-level alternative (a hand-rolled `hd` check, a proxy's `--email-domain`, an identity provider's e-mail regex) compares a **string**, which a consumer Google account carrying a verified address in the domain can satisfy without being a member of anything, whereas `domain:` resolves the principal against the Workspace **directory**. The design argument for that was written down when the plan was drafted; this is the observation that it behaves as argued. With it, plan 06 is archived and summarized in [docs/HISTORY.md](./docs/HISTORY.md), and [STATE.md](./STATE.md) has no active work for the first time since it was created — empty of candidate work too, since a tracker that lists issues nobody has started is a second backlog that drifts from the first. Nothing in this entry changes code: it records a verification and moves a plan's lifecycle, which is the point at which a plan stops being a thing anyone has to hold in their head.

- **A session trace is measured through the load balancer, closing the one thing plan 06 shipped unverified** (2026-08-09): slice 2 said plainly that IAP's behaviour against long-lived SSE was undocumented in both directions and would be checked by hand rather than asserted. It has been. A signed-in browser held a real session trace open through `${CONSOLE_HOST}` for **252 seconds** — eight times the 30-second GCLB default that `timeoutSec: 3600` replaces — and took all **sixteen** of the platform's 15-second `ping` frames, **each as its own chunk**. That last detail is the one that could not be inferred from configuration: it rules out the buffering that would matter — nothing in the path withheld the body waiting for the response to finish — and a buffering proxy is the other way SSE dies quietly, indistinguishable from a slow agent. Sixteen chunks at a 15-second cadence are evidence about this run rather than a proof that no buffer exists anywhere, which is the honest limit of what a single trace can show. The run carries its own control. The stream did not end by running out of patience; it ended on `event: session.deleted`, at the moment the probe session was deleted — so the connection was demonstrably alive and responsive right up to a shutdown for the reason the protocol defines, which is what separates evidence from an anecdote about nothing having gone wrong yet. Reading the reconciled load balancer rather than the manifest backs it up: `gcloud compute backend-services describe` reports `timeoutSec: 3600` on the GKE-generated backend service, so what this repository declares is what the edge actually runs, and [edge.yaml](./deploy/k8s/edge.yaml) now records both the measurement and its date beside the value. Two things are worth carrying rather than burying. Staging held **no agent, environment or session whatsoever**, so there was nothing to observe and the probe had to create three rows — an idle session with no `initial_events`, which is what keeps the agent loop and any model spend from starting, since the platform starts a turn only when initial events are present. And the cleanup is honest rather than complete: the session and environment were deleted and every default listing is empty again, but the agent could only be **archived**, because the platform offers no `DELETE /v1/agents` — agents are versioned definitions and archive is the terminal state it has. No `src/` changes, no test changes, no fidelity re-shoots.

- **The console's password leaves the cluster, and an unbounded rollback history turns out to be why it could not** ([#74](https://github.com/OpenSDLC-Dev/managed-agent-console/issues/74), 2026-08-09): `console-secrets` is down to one key. The deploy stopped reading `console-password` from Secret Manager, stopped masking it, stopped guarding it, stopped writing it into the Secret, and stopped folding it into `SECRETS_CHECKSUM` — which is now a plain digest of the one payload left. The console had not read the value since IAP became the gate; what kept it alive for another four days is the interesting part, and it is a general trap rather than a detail of this repository. **An old ReplicaSet keeps its entire pod template, `secretKeyRef`s included.** The Secret is written with `create … --dry-run=client | apply`, which replaces rather than patches, so while any revision from before the removal was still reachable, deleting the key would have made `kubectl rollout undo` restore a pod template the kubelet cannot start (`CreateContainerConfigError`) — turning the step whose entire purpose is to leave the last working console serving into an outage, in exactly the situation where something has already gone wrong. The consequence is worth stating in the general form: **with an unbounded revision history, no credential can ever be retired**, because there is always one more template holding it open, and "wait for enough deploys" is not a plan so much as arithmetic nobody performs. Six of the eleven surviving ReplicaSets still mounted the key, and the newest of them was seven ordinary deploys from falling off the end. So the fix is not to wait. `revisionHistoryLimit: 3` on the Deployment makes the reachable window a **stated bound** rather than a side effect of the default ten, and it is documented as a security boundary where it is set, not as housekeeping — three because the only automatic consumer is the workflow's rollback step, which names the revision that was serving before the run rather than counting backwards. Lowering it prunes **immediately**, not at the next rollout: applied to the live cluster it took the history from eleven ReplicaSets to four, and every survivor mounts `platform-api-key` alone. Two things were measured against the live cluster before the change landed rather than reasoned about from documentation. That `apply` genuinely **deletes** the key rather than merely ceasing to refresh it — a server-side dry run of the one-key Secret returned a merged object with `console-password` gone, because deletions come from the last-applied annotation, which still listed both. And that a pruned revision fails **loudly**: `rollout undo --to-revision=12` answers `unable to find specified revision 12 in history` and exits 1, rather than starting a pod that cannot resolve its Secret. The `kubectl set env … CONSOLE_PASSWORD-` line stays, with its job changed from repair to assertion — the rollback that motivated it can no longer happen, but a literal added to the live Deployment by hand would silently re-gate the console, where a hand-added `secretKeyRef` would now break the pod loudly, and this is what removes the quiet one. No `src/` changes, no test changes, no fidelity re-shoots: nothing the container runs is touched, and `CONSOLE_PASSWORD` remains the local-development and test variable it always was — the suites carry their own literals and never read this secret.

- **Plan 06 is delivered and verified in a browser** (2026-08-09): the staging console answers on a hostname over HTTPS, and the only way in is a Google account in the Workspace domain. Confirmed against the live deployment rather than inferred from a green pipeline: the pod's environment is `PLATFORM_BASE_URL` and `PLATFORM_API_KEY` and nothing else — **no `CONSOLE_PASSWORD`, so no authentication code runs in production at all**; anonymous `GET /` and anonymous `GET /api/platform/v1/agents`, both sent with `Accept: application/json`, answer 401 carrying `x-goog-iap-generated-response`; and a signed-in Workspace account reaches `/agents` directly, with no password page in the path and the platform reporting connected. The `Accept` header is not decoration and is why the assertions send it explicitly — IAP content-negotiates its refusal, so a default `curl` (`Accept: */*`) is read as a browser and gets **302 to `accounts.google.com`** instead. Both carry the header; only the code differs. One claim is deliberately **not** made: that a Google account outside the Workspace is refused. That needs a second account to sign in with, and asserting it from the IAM binding rather than from an attempt would be exactly the kind of reasoning this work has been catching all day. It is recorded as unverified in [STATE.md](./STATE.md) instead.

- **Removing an environment variable is now stated, because `apply` cannot be relied on to imply it** (2026-08-09): the deploy that was to complete the password removal rolled back instead, reporting `401 {"type":"authentication_error","message":"console login required"}` from the in-pod deep check — a revision whose manifest had not mentioned `CONSOLE_PASSWORD` for two commits, serving as though it had one. It did have one. `kubectl apply` computes deletions from **(last-applied − new config)**, and `env` merges by `name`, so an entry is dropped only if it was in the previously applied configuration and is absent from this one. The first deploy of the passwordless manifest removed it correctly; that deploy then failed a later gate and `kubectl rollout undo` restored the whole previous pod template — `CONSOLE_PASSWORD` included — **without touching `last-applied-configuration`**. From that point the entry was live, absent from last-applied, and absent from the manifest, so every subsequent apply saw nothing to delete and preserved it indefinitely. A rollback had made a removal permanently unrepeatable, and the symptom pointed at the application rather than at the deploy. Server-side apply does not fix this, which was measured rather than assumed: `--force-conflicts` takes ownership of fields the manifest _specifies_ and says nothing about a field another manager added that the manifest simply omits. Both forms were run with `--dry-run=server` against the live object and both kept the variable. The workflow now **states** the removal — `kubectl set env deployment/console CONSOLE_PASSWORD-` — which is idempotent (removing a variable that is not there exits 0 and changes nothing), so it is a no-op on every ordinary run and the only thing that works on the run after a rollback. `deployment.yaml` says so at the point where a reader would otherwise conclude that absence is sufficient. **And the rollback now names its target**, which the same change made necessary: `kubectl rollout undo` defaults to `--to-revision=0`, meaning "the revision before the current one" rather than "the last one that worked". A single deploy can now produce two revisions — the apply, then the `set env` — so on the run where the removal actually does something, the default would restore the revision _between_ them: this run's unverified image, still carrying the password it was supposed to lose. The job captures the serving revision before it touches anything and rolls back to that number, which also removes the question for any future change needing two steps. When there is no such revision — a first deployment, or one the selector guard recreated — the step says so and refuses rather than guessing, and `kubectl` exiting 1 on an unknown revision was checked rather than assumed.

- **The deploy's reachability check stops needing a permission CD does not have** (2026-08-09): the first real run of the rewritten smoke gate failed, rolled itself back, and left the previous revision serving — which is the gate working, but on a defect introduced with it. The new check read the backend's health with `gcloud compute backend-services get-health`, and the deploy identity holds exactly what CD needs — push images, drive the cluster, read secrets — and **no compute permissions**, by a design this repository states in as many words. So it died on `Required 'compute.backendServices.list' permission`, and the error message it printed said _"the Ingress has not produced one"_ — confidently wrong, because it could not tell "there is no backend" from "I am not allowed to look". It now reads the same state from the Ingress' own `ingress.kubernetes.io/backends` annotation, which the ingress controller publishes from GCLB and which `kubectl` can already see. The alternative was widening the deploy identity to read all of Compute in order to run one assertion, which trades a standing permission for a line of convenience. The check is keyed on `-console-` so the cluster's `default-http-backend`, which shares that annotation, cannot answer for the console, and it requires **every** matching backend to be `HEALTHY` rather than the first — exercised against the live cluster with three negative controls (no match, `UNHEALTHY`, and a mixed set), because a health check that cannot fail is not one.

- **Google sign-in gates the staging console; the shared password leaves production** (2026-08-09, plan 06 slice 2): the staging console is now reachable only by a Google account in the maintainer's Workspace domain, enforced at the load balancer by **GCP IAP** — and the production container ends up with **no authentication code running in it at all**. It did not gain a login; it lost the one it had. `CONSOLE_PASSWORD` is no longer set in the pod, so [src/proxy.ts](./src/proxy.ts) returns `next()` before any check, which is the correct posture rather than a gap: a request that reaches the process has already been authorized by something the process cannot be talked out of. Three lines of `BackendConfig` switch IAP on, and **no OAuth client secret enters the cluster or this repository** — omitting `oauthclientCredentials` selects the Google-managed client (GKE 1.29.4+), which is the single largest reason this option is smaller than running an identity provider. Who is admitted is deliberately not in git: `roles/iap.httpsResourceAccessor` bound to the Workspace domain, on the **backend service** rather than the project. IAM inherits downward, so a project-level grant would apply to every IAP-secured resource in the project including ones that do not exist yet — the next application to enable IAP would be open to the whole domain the moment it was switched on, silently, with no separate grant for anyone to review. The `domain:` form also resolves the principal against the Workspace **directory**, where every application-level alternative — a hand-rolled `hd` check, a proxy's `--email-domain`, an identity provider's e-mail regex — compares a **string** that a consumer Google account carrying a verified address in the domain can satisfy without being a member of anything. **Removing the password opens a second door, and closing it ships in this same commit rather than after it.** The container listens on `0.0.0.0:3000` and, with no gate of its own, was reachable by every workload in the cluster with a management-key-injecting proxy behind it; a new `NetworkPolicy` admits port 3000 only from Google's load-balancer ranges (`35.191.0.0/16`, `130.211.0.0/22`). The obvious-looking alternative is **wrong here and would break the deployment**: binding the container to `127.0.0.1` does not narrow the exposure but removes it from the load balancer, because container-native load balancing delivers straight to the **Pod IP** — and it fails quietly, since the kubelet probes inside the container's network namespace, so readiness goes green, `rollout status` succeeds, and the hostname serves 502 from a backend that can never pass its health check. Verified against the live cluster before merging rather than reasoned about: a probe pod reached the control plane (TCP established, HTTP 401 back) and **timed out** against the console pod's 3000, while the pod stayed Ready and the GCLB backend stayed `HEALTHY`. **The credential leaves the pod now and the cluster later, and that split is deliberate rather than a half-measure.** Every revision in the Deployment's history from before this change still mounts `console-password`, and the Secret is written with `create … --dry-run=client | apply`, which **replaces rather than patches** — so dropping the key would make `kubectl rollout undo` restore a pod template the kubelet cannot start (`CreateContainerConfigError`), turning the step whose entire purpose is to leave the last working console serving into an outage, in exactly the situation where something has already gone wrong. The pipeline therefore still writes both payloads; the empty-`console-password` guard survives with a rewritten message, because it now prevents a different failure than the one it was written for. **The order of the apply is itself part of the gate**, for the same class of reason: `iap.enabled` is a _request_ to the ingress controller rather than an immediate state — about two minutes here — so applying everything at once would roll a passwordless pod into a backend whose gate was still opening, and noticing the IAP header afterwards does not undo having served. The edge, the `NetworkPolicy` and the Service go first, the job waits for the hostname to actually refuse an anonymous request, and only then is the Deployment applied. The smoke gate is rewritten around the fact that **every path through the front door is now 401**, so a request can no longer tell "gated" from "broken": reachability is taken from the load balancer's own view (`get-health` must report `HEALTHY`, the same signal it routes on), and the gate is asserted twice — anonymous `GET /` **and** anonymous `GET /api/platform/v1/agents`, the path that actually spends the management key. Both must carry **`x-goog-iap-generated-response`**, not merely answer 401: a 401 can come from the application, from a misrouted backend, or from a load balancer with no policy on it whatsoever, and every one of those passes a bare status check while the gate is simply absent. That header is the only part of the response nothing but IAP can produce. The in-pod deep check loses its login preamble and collapses to a single fetch, run over loopback because the CD job holds no Google identity IAP would accept — the supported path rather than the only reachable one, since IAP refuses **anonymous** callers and a signed-in member of the Workspace can still fetch `?deep=1` from a browser. That is not an escalation and the comments now say so plainly: the same person can drive every page of the console, and every page spends the same key. What this deployment removes is the anonymous internet and the rest of the cluster, not the operator. **No `src/` behaviour changes, no test changes, no fidelity re-shoots** — `CONSOLE_PASSWORD` remains the local-development and test credential, the suites carry their own, and `/login` still exists and still renders. Carried knowingly: `domain:` admits every present and future account in the Workspace; the backend service's name is generated by GKE, so recreating the Ingress or Service requires re-applying the binding — until it is, the console is closed to everyone rather than open to anyone; and IAP's behaviour against long-lived SSE is undocumented in both directions and is checked by hand rather than asserted.

- **The staging console gets a hostname and TLS** (2026-08-09, plan 06 slice 1): staging was a `type: LoadBalancer` Service on port 80 — a bare public IPv4, no domain, no certificate — with a shared password typed over it in the clear and a full-power platform management key behind that. It now answers on the hostname in the `CONSOLE_HOST` variable, over HTTPS, behind a global external Application Load Balancer with a Google-managed certificate; plain HTTP redirects rather than being refused, so typing the bare hostname still works. **The gate is untouched** — the password stays, `307 → /login` stays the assertion, `src/` is not modified and no test or fidelity surface changes. This slice is independently valuable even if the rest of plan 06 were abandoned: it stops the password and every session cookie crossing the wire in the clear. New `deploy/k8s/edge.yaml` carries four objects, and **two of its settings exist only because the load balancer's defaults break this application silently**. The health check is pinned to `/api/health` on port 3000, because the default is `GET /` — which this application answers with a 307 whenever the login gate is on, and which GCLB reads as unhealthy: the default produces a **permanently 502 hostname while the pod is Ready, `rollout status` is green and the logs are clean**, with nothing in the cluster looking wrong. And `timeoutSec` is 3600, because the GCLB backend timeout defaults to 30 seconds and is a **request-and-response** timeout rather than an idle one — it caps the whole exchange regardless of traffic, so a session trace's SSE would be cut every 30 seconds while the browser reconnects with backoff and re-walks history, a console that looks slow and drops events while reporting nothing anywhere. The `kubernetes.io/ingress.class: gce` annotation draws a deprecation warning from the API server that must **not** be acted on: GKE's controller keys off the annotation, and this cluster has no `IngressClass` objects at all, so `spec.ingressClassName` would name nothing and leave an Ingress no controller claims — one that never receives an address. The Service becomes `ClusterIP`, which is correct only because the cluster is VPC-native and the load balancer is therefore container-native, delivering to the Pod IP through a NEG; on a cluster that is not, this would be `NodePort` and the health check would name the node port. CD gains the host as a rendered placeholder — `CONSOLE_HOST`, a bare word like `CONSOLE_IMAGE`, since `kubectl apply` substitutes nothing and a leftover `${…}` in `ManagedCertificate.spec.domains` is a rejected DNS name rather than a readable error — loses the external-IP polling loop a `ClusterIP` Service can no longer satisfy, gains an assertion that plain HTTP redirects, and **checks the certificate reports `Active` before it tries the hostname at all**: first issuance takes 15–60 minutes and cannot be hurried, so without that check a still-provisioning certificate presents as a five-minute TLS timeout followed by the pipeline rolling back a revision that is in every way healthy. Three things stay human-driven and out of CD, consistent with the rest of this pipeline: the **global** static IP (a global forwarding rule cannot take the old regional address, so **the console's public IP changed**), the **DNS-only** A record pointing at it — a CDN-proxied record resolves to the provider's anycast addresses, so Google never sees what it needs and the certificate sits at `FAILED_NOT_VISIBLE`, which reads as "still waiting" rather than as "misconfigured" — and the first issuance itself. What this does not change: the password is still a shared secret and still the only thing in front of the management key. TLS fixed the wire, not the authentication.

- **Deployment identifiers leave the public repository** (2026-08-09, issue #69): `.github/workflows/deploy.yml` named one GCP project, one zone, one cluster, one namespace, one Artifact Registry path, one Workload Identity Federation provider and one deploy service account, and `deploy/k8s/deployment.yaml` named the control plane's in-cluster Service; `docs/deploy-gcp.md` and `deploy/k8s/README.md` repeated them. **None of it was ever a credential** — there is no service-account key, WIF only trusts tokens from this organization's repositories, secrets are read from Secret Manager inside the job — but a public repository that names them hands a reader a target list, and, more importantly, ties an open-source project to one operator's cluster: someone cloning this to run their own console inherited manifests they had to edit and documentation describing a cluster they could not reach. All of it now comes from GitHub Actions **variables** (not secrets, because they are not secret), and the deployment files refer to them by name. `deployment.yaml` gains a `CONTROLPLANE_URL` placeholder beside the existing `CONSOLE_IMAGE` and `SECRETS_CHECKSUM`, substituted by the same `sed` — spelled deliberately unlike the `PLATFORM_BASE_URL` container variable it is assigned to, because a `sed` on that word would rewrite the `name:` key beside the value and produce a variable called `http://…`. The placeholders stay **bare words** rather than `${SHELL_STYLE}` for a reason the manifests make sharp: `kubectl apply` substitutes nothing at all, so a shell-shaped token that escaped the rendering step would reach the API server with its dollar and braces intact, as part of a DNS name. The workflow's **first step now asserts every variable is set and non-empty**, before it authenticates or builds — an unset variable renders as the empty string rather than failing, and `gcloud --project ""`, `kubectl -n ""` and an image tag with no repository all fail late and confusingly; whitespace-only counts as unset, on the same reasoning as the existing empty-password guard. What this does **not** do is retroactive: the literals remain in both repositories' git history, and rewriting the history of two repositories that have cut releases was declined deliberately — these are identifiers, not credentials, and the trust policy is what protects the deployment. `deploy/` is now documented as what it is, a **reference deployment rather than a template**.

- **Plan 06 approved — Google sign-in replaces the shared password on staging** (2026-08-09): staging is a shared password typed over plain HTTP into a bare public IPv4, and what sits behind it is a full-power platform management key. [docs/plan/06_google-sign-in.md](./docs/plan/06_google-sign-in.md) scopes two slices to replace it with **Google sign-in restricted to `@${WORKSPACE_DOMAIN}`, enforced at the load balancer by GCP IAP**, after which the production console has no authentication code at all — it loses the five files it has rather than gaining more. The maintainer asked first whether the [casdoor/casdoor](https://github.com/casdoor/casdoor) checkout he keeps could serve this. It could, and should not: 88k lines of Go, 309 module requirements, a 319-file React admin, an LDAP and a RADIUS listener started unconditionally (`main.go:144-152`) and a first-boot `built-in/admin` / `123` (`object/init.go:170`), to express a rule whose only working form there is a one-row whitelist — and via a field that is **broken**, since `Provider.EmailRegex`'s reject branch at `controllers/auth.go:932-935` has no `return` and `ResponseError` does not abort the Beego handler, so a rejected address falls through into sign-in at :938 (the adjacent branch at :930 does return, so this is an omission rather than a soft warning). The blocker that outranks the choice, and applies to every option including Casdoor: **Google will not issue this flow against the deployment as it stands.** Two independent rules for a Web application OAuth client, each exempting localhost only — redirect URIs must use HTTPS, and hosts cannot be raw IP addresses — so a hostname with TLS is a precondition, not a preference, and putting any third-party IdP in front does not dodge it because that IdP's own callback host is what Google validates. IAP wins on three grounds: it is the literal reading of principle 5 ("deployment protection, not a user system") since deployment protection belongs to the deployment; the IAM binding `domain:${WORKSPACE_DOMAIN}` resolves the principal against the Workspace directory, where every application-level alternative — a hand-rolled `hd` check, a proxy's `--email-domain`, Casdoor's `EmailRegex` — compares a string that a consumer Google account carrying a verified `@${WORKSPACE_DOMAIN}` address can satisfy without being a member of anything; and nothing in the repository becomes GCP-specific, since a self-hoster keeps `CONSOLE_PASSWORD` and the published image is byte-identical in behaviour. oauth2-proxy is recorded as the documented upgrade path rather than adopted — it buys issuer portability the console does not yet need, for a container to patch, two new secrets and a weaker domain rule. Four things the drafting turned up that the plan now carries as work rather than as discoveries. **The gate fails open and D2 makes that the production posture**: `src/proxy.ts:5-6` returns `NextResponse.next()` before any check when `CONSOLE_PASSWORD` is unset, so removing the password needs zero `src/` changes — and `src/app/api/health/route.ts:62` stops self-gating at the same moment, which opens `?deep=1`, the lever that spends the management key, to anyone who can reach the port. **The container listens on every interface** (`Dockerfile:30` is `HOSTNAME=0.0.0.0`), so port 3000 is reachable on the pod IP cluster-wide with a management-key-injecting BFF behind it; closing that ships in the same PR as the password removal, because the reverse order is the one sequencing error the plan cannot absorb. **Two silent traps in the GKE edge**: the default Ingress health check is `GET /`, which this app answers 307 and GCLB reads as unhealthy — a permanently 502 hostname while the pod is Ready, `rollout status` is green and the logs are clean; and the GCLB backend timeout defaults to 30s and is a request-and-response timeout rather than an idle one, so a session trace's SSE is cut every 30 seconds while the client reconnects with backoff and re-walks history, reporting nothing. Both are pinned in `BackendConfig`. **CD assumes a password in five places** that become wrong at once: the empty-payload guard that refuses to deploy without one, the two-payload `SECRETS_CHECKSUM` that makes a rotation actually roll the pod, the in-pod deep check whose first statement throws without it, the `login_gate == true` assertion whose subject becomes permanently false, and the anonymous `GET /` → 307 `/login` assertion the edge now answers instead. Verified against the live project rather than assumed: the deployment project is parented to the Workspace organization, so the `domain:` binding and an Internal consent screen are both available — the organization and customer identifiers are deliberately not reproduced in the plan, which gains a section on why `deploy/` in a public repository is a reference deployment rather than a template, with the broader work of parameterising it out of both repositories filed separately rather than smuggled into an authentication change; and `${WORKSPACE_DOMAIN}` resolves `MX 1 smtp.google.com` on Namecheap nameservers, so the one DNS record is a manual edit next to live Workspace mail. Recorded as carried risk rather than solved: the public IP necessarily changes (a global forwarding rule cannot take the passthrough NLB's regional address), the production container has no gate of its own by design, `domain:${WORKSPACE_DOMAIN}` admits every present and future Workspace account, IAP's behaviour with long-lived SSE is undocumented in both directions, and none of this covers the platform's own API — which keeps its public load balancer and its `x-api-key` untouched.
