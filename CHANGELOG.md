# Changelog

Notable changes, newest first. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/); each entry is the one place a change's narrative is written.

This file holds the cycle in progress. **Released cycles live in [docs/changelog/](./docs/changelog/)**, one file per version — entries here are narrative paragraphs, and a single file accumulating them would make every reader pay for the whole project's history to see what changed this week.

## [Unreleased]

Two plans drafted for the console half of the platform's SSO and RBAC work: [plan 07](docs/plan/07_console-issued-keys.md) builds the credential-issuance surfaces (environment keys, API keys) — absorbing the earlier environment-keys-only draft of plan 07, whose decisions taken with the maintainer on 2026-08-10 carry forward unchanged — and [plan 08](docs/plan/08_console-sso-rbac.md) adds a browser OIDC login and forwards the signed-in operator's own token in place of the management key on user-initiated calls, keeping the `x-api-key` path intact for the deployment's own health check and for identity-disabled deployments. Neither is approved yet — each opens with the decisions its author could not make alone, and plan 08's first one is worth naming: the platform's plan 31 assigns this repo a topology in which the browser calls the platform directly, which discards the mechanism the console's principle 2 names, though not the guarantee behind it.

Plan 07's first slice lands its seams, and nothing observable changes yet: the console gains a second BFF namespace, `/api/oauth/...`, for the platform's off-wire console API. It is deliberately not a second passthrough — the `/api/platform` proxy forwards any `v1` path, which is right for a wire surface the console reaches whole, but a namespace holding exactly two routes gets an allowlist instead, so a management credential cannot be lent to an arbitrary upstream path by a request the browser composes. Both proxies now share one forwarding core rather than two drifting copies of the header rules. Alongside it: the offset-pagination envelope (the console API's list shape is neither of the two the wire uses), the environment-key wire types and their zod transcription, the query hooks, and a `consolePostNoContent` helper — revoke succeeds as a bodiless 204, and every existing helper parses a JSON body on success, so without it a successful revoke would have surfaced as an error toast.

Review of that slice turned up a hole in the older proxy as well, and it is worth stating plainly because it predates this work: a gate checks a path _string_, and `fetch` then reparses the URL built from it. WHATWG URL resolution collapses dot segments, so a segment that is exactly `..` could satisfy a gate and be sent somewhere else entirely — `/api/platform/v1/../../admin/keys` left the `/v1` surface and arrived at `/admin/keys` with the management key attached. Percent-encoded spellings reach the same place by a longer route, because Next decodes the catch-all once per segment and the URL standard resolves `%2e%2e` as `..` too. The guard now sits in the shared forwarding core, so both proxies and any route added later inherit it, and the console-API gate states its id slots as an id charset rather than "anything without a slash".

The mock platform learned the same three routes, and one of them taught us something the mock had wrong: revocation is idempotent. The platform's UPDATE matches on key id and environment alone and coalesces the timestamp, so revoking an already-revoked key answers `204` a second time, and only an id the environment never issued reaches the `404`. The mock had been deleting the row, which would have answered `404` — an e2e test written against it would have encoded a contract the platform does not offer. Both the mock and the conformance suite now carry the real semantics, checked against a running platform in Chrome on 2026-08-14 alongside the rest of the protocol: the list envelope, the `{"name": …}` create body, the `{access_token, expires_in}` response with its `no-store` header, and the allowlist refusing four shapes of out-of-scope request without contacting the platform at all.

Slice 2 makes the keys visible: a self-hosted environment's detail page now carries an **Environment keys** section listing what has been issued, with the id, when it was created, and when it expires. Expired keys are listed rather than hidden, because the platform serves them on purpose — an operator whose worker has stopped connecting needs to see the credential it is failing on — so each row also says which state it is in, and says it in a `data-key-state` attribute as well as a badge. A cloud environment has no worker to hold a key and gets no section at all; an archived one keeps its section, because keys already handed out must stay revocable after the environment is put away.

Two decisions the plan had deferred to this slice are settled in it. There is **no pager**: the platform's page size is both the default and the maximum at 100, an environment realistically holds one key per host, and a surface that would need paging instead says so in a line naming how many keys exist — silently showing the first hundred of more would read as completeness. And the section **feature-detects a platform that predates the console API** by reading a 404 on the tokens route as "not served here", which is safe only because the page has already loaded that environment successfully — with the three ways `consoleEnvironment` can answer 404 thereby closed, the router catch-all is what remains. The reasoning is written down in `docs/wire-divergences.md` rather than left in a comment, because it is an exception to the collection-route rule the rest of the console's feature detection rests on.

Slice 3 makes the surface usable: an operator can now **issue** an environment key and **revoke** one, and the page carries the reference's four-step setup guide beside the table, in the two-column layout the reference uses. Issuing prompts for a name, then swaps to a reveal-once dialog — the platform returns the plaintext exactly once and never again, so that dialog is the only place it is ever rendered, it offers a copy button, and it says plainly that closing is final. Because the issuance response identifies no row, the list is re-read rather than rendered from the response, which is the reference's own sequence. The generate control is hidden for the two cases the platform refuses outright — a cloud environment and an archived one — while an archived environment keeps its table and its revoke buttons, since keys already handed out must stay revocable.

The adversarial probe written for that dialog found a real leak, which is the reason it exists. The plan had recorded that `mutation.reset()` takes the plaintext out of the mutation cache; it does not — it detaches the observer and leaves the cached mutation, so the key would have outlived the dialog that showed it by the default five-minute retention, reachable from anything that walks the cache. The mutation now carries `gcTime: 0`, and the probe asserts the secret appears in the DOM exactly once, in no attribute of any element, and in neither cache nor storage once the dialog closes.

Review caught a second way the one-time key could go astray, and it is the sharper of the two: the create dialog could be dismissed — by Escape, the close control, or an outside click — while the POST was still in flight. The platform mints the key the moment that request lands, but dismissing detached the mutation observer, so the handler that captures the plaintext never ran. The operator would have been left with a live credential nobody had ever seen, revocable only blind. Dismissal is now refused while the request is in flight, which is the honest shape for an operation that is short, uninterruptible, and hands back something unrecoverable.

The axe pass over the new dialogs turned up two more things. One was ours and is fixed: the setup guide's code blocks scroll horizontally, and a scrollable region that cannot be focused is readable only with a mouse. The other is not ours and is now [#90](https://github.com/OpenSDLC-Dev/managed-agent-console/issues/90) — the shared `destructive` button variant fails colour contrast, which affects every archive and delete confirm in the console and has been shipping unobserved because no a11y test had opened one. The new test asserts zero violations across the surfaces this slice introduces and stops short of that shared control rather than suppressing the rule.

Plan 07 carries a recording of the reference console's key-management dialect, made in Chrome on 2026-08-14 against a live Admin session. It confirms the paths the platform already mirrored, adds the request bodies for both issuance calls, and documents how the reference gates its UI — a bootstrap capability manifest of `{permission, status}` pairs rather than a role name. Plan 08's D4 asks the platform for a `me` route and, absent one, ships optimistic UI with a 403 toast; whether that route should carry permissions or a role is an open decision there. The recording was taken without minting anything: submissions were intercepted and refused, and the account's credential lists were re-read afterwards to prove it.

Plan 08 leaves draft on its own recommendations, and its first slice lands the configuration everything after it needs — with nothing user-visible yet. The console learns to read `IDENTITY_*` variables, using the platform's own names because two of the values have to agree across the two processes: the issuer, and the console's client id, which is what the platform must be configured to expect as `IDENTITY_OIDC_AUDIENCE` — in an authorization-code flow an ID token's `aud` **is** the relying party's client id, so two different values would produce tokens the platform rejects on every proxied request. The URL rules are transcribed from the platform's verifier rather than invented (https or http-to-loopback, no credentials in the URL, no query or fragment on an issuer), because a URL this console accepts and the platform refuses is a deployment that boots and then cannot serve. Its defects fail **closed**: a console that cannot parse its own identity configuration cannot authorise anybody, so it reports 503 rather than quietly serving as though identity were off, and it never falls back to the management key. Plan 08 D3's four-configuration matrix is encoded as a function and pinned row by row before anything has a UI, because the dangerous row — both the password gate and identity configured — is only dangerous relative to the other three, and an unspecified overlap is exactly where a password session silently reacquires root.

Two deployment landmines the plan had named are defused in the same slice, both of which would have detonated later. **`PLATFORM_API_KEY` stops blocking readiness once identity is configured.** The Kubernetes readiness probe takes the shallow health depth, and an identity-mode deployment needs no management key to render a page — browser-initiated calls carry the operator's own token — so leaving it required would have made such a rollout permanently NotReady over a credential it does not use, in a way that reads as an infrastructure fault. What the key remains there is the deep check's dedicated service credential, the one console→platform call that can never act as a user because CD runs it with no user in sight; asked for that depth without it, the route now answers `degraded` and `platform.checked: false` rather than inventing "unreachable", since "no service credential" and "the platform is down" call for opposite fixes. Review caught the first version of this making the key optional **unconditionally**, which is a different and much worse claim: with identity off the BFF resolves it on every proxied request and 500s without it, so a Ready pod would have answered nothing but errors. The condition is exactly whether browser calls still spend the key — which is the predicate the mode matrix already computes, and the reason it was worth writing down before anything consumed it. And the session cookie's `Secure` flag now comes from `x-forwarded-proto` rather than the request's own protocol, which is plain `http:` on every deployment in `deploy/` because a load balancer terminates TLS: harmless while production sets no `CONSOLE_PASSWORD` and mints no cookie at all, a live bug the moment plan 08 mints one. The two signals are OR'd rather than the header simply winning, so a client-supplied header can only add the flag, never strip it from a cookie minted over a connection that really was TLS. Identity configuration is also a new probe-ratchet seam: its complaints are served to an anonymous caller, so they name variables and never quote values — a stronger property than redaction and cheaper, and one no happy-path assertion can see, because a working console never takes that path. Checked end to end against a running platform in Chrome on 2026-08-14 rather than reasoned about: the deep check answering 200 with `checked: true`, an identity-configured process reporting `mode: oidc` while its body carries neither issuer nor client id nor secret, sign-in landing on the console with the cookie invisible to JavaScript, the same login request minting `Secure` only when a proxy says the browser used TLS, a broken identity configuration answering 503 with `missing` and `invalid` separated, and a console with no management key at all reporting Ready — with identity configured — while its deep check reports degraded.

**The console can sign an operator in.** Plan 08 slice 2 lands the OIDC relying party under `/api/auth/…` — `login`, `callback`, `logout` — and with it the first new runtime dependency since plan 01 (`jose`; the repo had no JWT tooling at all). The flow is authorization code with **PKCE (S256)**, and every endpoint it uses is read from the provider's own discovery document rather than guessed: `/protocol/openid-connect/auth`, `/login/oauth/authorize` and `/o/oauth2/v2/auth` are three different answers to the same question, and only the provider knows which — a point the verification made concrete when a real Casdoor turned out to serve the second. Discovery is validated as remote input even though the operator configured it: the document must name the same issuer it was fetched from (OIDC Discovery §4.3, and `iss` is compared as an exact string by the platform's verifier downstream), every endpoint gets the same scheme rule the issuer does, and the read is bounded so a provider that streams without end costs a request rather than the pod.

Three things are proven before a session is minted, and they are three because each closes a different hole. **The state cookie** proves this browser started a flow: remembering `state` server-side alone would let a third party start one, keep its `state`, and walk a victim through the callback to land the attacker's identity in the victim's console — login CSRF, whose whole point is that nobody notices. **The pending record is read once and removed**, so a callback URL replayed out of history, a referrer or a proxy log cannot mint a second session from one authorization. **The nonce** ties the ID token to this browser's request; without it a token captured from any other flow for the same client would complete a sign-in here. The token itself is verified against the provider's JWKS rather than trusted for having come over TLS — OIDC Core §3.1.3.7 permits skipping that, but the platform will check the same signature on every proxied request, so a token this console accepts and the platform rejects is a deployment that signs people in and then serves them 401s.

The tokens never reach the browser: it holds an **opaque handle** and the ID token stays in a server-side store (plan 08 D2), which is the console's first stateful component and says plainly what that costs — one replica only, and every deploy signs every operator out, on a console redeployed on every merge to `main`. The pending map is capped and swept because `/api/auth/login` is anonymous by construction and an uncapped map there is a memory exhaustion costing an attacker one GET per entry. Nothing the provider or the query string says is ever reflected back: failures become one of four console-authored codes that the login page explains in its own words, so a callback anyone can reach cannot put text on a page wearing this deployment's hostname. And `return_to` is narrowed to a same-origin path, because an open redirect there would be the same trick with the same hostname.

Two supporting changes. `src/proxy.ts` exempts the whole **`/api/auth/` prefix** — the plan's third landmine, and the one exemption that is a namespace rather than an anchored route: nobody holds a session before signing in, so a gated `/api/auth/login` would bounce the browser to `/login` and a gated callback would drop the provider's redirect on the password form, and the sign-in could never complete on any deployment that also sets `CONSOLE_PASSWORD` — which is local development, the gated e2e specs and the fidelity run. The trailing slash is what keeps it narrow, and a test pins that `/api/authorize` stays inside the gate. And **CLAUDE.md principle 5 is amended**, which the plan scheduled for this slice: it forbade RBAC/SSO outright "until the platform grows them", and the platform has now grown them. What replaces it keeps the reason rather than the prohibition — the console runs a browser sign-in, will forward the operator's own token once slice 3 lands, and still never mirrors the platform's claim→role mapping or decides who may do what.

Review caught the gap that slicing left open, and it is the sharpest finding on the change: with identity configured and no `CONSOLE_PASSWORD`, `src/proxy.ts` returns `next()` before any check and the BFF was still attaching the management key — so a deployment that opted into SSO would have been **less** protected than one that had not, while showing a sign-in page that implied the opposite. **The BFF now fails closed in identity mode**: no valid session, 401, and the management key is not sent. Swapping the credential a signed-in operator's calls carry is still slice 3's; refusing an anonymous one could not wait. The check lives in the BFF rather than the matcher for a structural reason worth writing down, because slice 3 inherits it: middleware runs in the Edge runtime and cannot see the session store, which is Node-side module state — and it does not need to, since every byte a page renders comes through the proxy. Three more review findings, all real and all fixed: the Basic credential was built with `encodeURIComponent` where RFC 6749 §2.3.1 wants form-urlencoding (a client secret containing a space would have been decoded as a different secret and refused on every exchange); `jose` enforces `exp` only when it is present, so a token carrying none would have verified into a session that had already expired; and the login page's error map was a plain object, so `?sso_error=constructor` reached an inherited function that `??` does not catch and React will not render — an empty alert where the generic line belongs.

Verified in Chrome against a **real Casdoor**, which is worth more than a mock here because a mock would have agreed with whatever the console sent: the console discovered the provider, built an authorization request carrying `response_type`, `client_id`, `redirect_uri`, `scope`, `state`, `nonce`, `code_challenge` and `code_challenge_method=S256`, bound that `state` to an httpOnly cookie on the same narrow path, and the provider **accepted** it and rendered its own sign-in page. Completing the round trip needs an operator's own credentials, so it is not claimed here; it is plan 08 slice 5's acceptance. What was exercised for real beyond that: an unreachable issuer producing the console's own "could not be reached" line with no provider text on the page, and two forged callbacks — one with no state cookie, one whose cookie named a different flow — both refused with `state_mismatch` and no session minted. Surfaces re-shot: `login`, in all three configurations it can be in.

**The console now acts as the operator, not as root.** Plan 08 slice 3 swaps the credential a browser-initiated call travels under: in identity mode the BFF sends `Authorization: Bearer <the operator's id_token>` and **does not read `PLATFORM_API_KEY` at all**. The two are never sent together, and that is the sharpest rule in the change rather than a tidiness preference — the platform's dispatcher gives a request carrying a non-empty `x-api-key` to the management lane outright and never looks at the Bearer (`internal/api/server.go`, `dispatchManagementAuth`/`apiKeyOffered`), so a console that attached both would erase the operator's role and serve them as root, succeeding every time and failing no test that only checks for a 200. With identity off nothing moves: `x-api-key`, no `Authorization`, byte for byte what shipped before.

A 401 from the platform is now treated as the end of the console's session rather than as one more failed request. The session is destroyed, the handle is cleared, and the browser is sent to the login page carrying where it was — so an operator whose token expired mid-session lands back on the page they lost instead of on a list of red toasts. The signal is a response header the BFF sets on refusals **it** authored, and the reason it is not simply the status code is worth stating: a 401 also means "this deployment's management key is wrong", and bouncing that operator to a sign-in would send them through a flow that cannot fix it, or around a redirect loop on a deployment whose `/login` is the password form. A header rather than a body field, because the proxy streams upstream bodies through untouched and the trace reader never parses an envelope. The live trace loop reads it too: a dead session is the one drop reconnecting cannot repair, and without this the trace would have sat at a 15-second backoff saying "reconnecting" while the real answer was that nobody was signed in.

Review caught the consumer that had been missed, and the case it breaks is the quiet one. The shell's 30-second connection poll fetches the BFF directly rather than through the shared helper, so it read a sign-out as an outage — and on an idle page it is the _only_ consumer still running, which means an operator whose token had just been revoked would have sat in front of "Platform unreachable" with a live event trace still streaming beside it, and nothing left to notice. There are exactly three direct consumers of the BFF in the console; all three now read the marker.

The mock platform learned the same credential dispatch — machine key first and outright, then the human lane, then the unchanged `missing x-api-key header` that tells an unauthenticated caller nothing about whether SSO is on — plus a hook that makes it refuse a token the way a provider revocation would. Its lane is asserted in the conformance suite rather than left for the acceptance slice: a JWT-shaped Bearer is accepted, a request carrying both credentials lands on the management lane, and an `sk-map-env01-` Bearer is not mistaken for a human. The BFF is also a new probe-ratchet seam, which it should have been before: it is where the choice between the two credentials is made, and every happy-path assertion there passes whichever one travels.

Verified end to end in Chrome against a **purpose-built OIDC provider that auto-approves**, because the point was to reach the signed-in half without anyone typing a password — and the provider was made strict where the console's correctness was the question, so it refuses a wrong PKCE verifier and decodes the Basic credential per RFC 6749 §2.3.1 with a secret containing a space and a plus, which is the encoding bug PR #94's review caught. The console was run with **no `PLATFORM_API_KEY` in its environment at all**: visiting a page bounced to `/login?return_to=…`, the sign-in came back to the page that had been asked for, and the lists rendered — which they could only do on the operator's own token. The one hop DevTools cannot show was captured from an upstream that prints what it receives: every request `Authorization: Bearer` with a two-dot compact JWS and `x-api-key` absent, and the same console with identity off sending `x-api-key` and no `Authorization`. Then the platform was made to refuse the token: the refusal came back carrying the platform's own message and the console's marker, and the next page load bounced to the login page. Surfaces re-shot: `login` — unchanged, as expected, since the slice adds no visible element to it.

**A refusal now reads as a refusal.** Plan 08 slice 4 gives the console the other half of acting as a person: with roles enforced per route, an operator will be told no, and until this slice a `403` arrived dressed as a fault — red text, "Request failed", a retry that answers the same way until somebody changes a role. A denial is now separated from a failure everywhere the console reports one. The page-level error state drops the destructive red and keeps the platform's own sentence; the toast is titled "Not permitted" unless the call site chose a title of its own; and both append one line the platform's message cannot supply — that it names **the role the route requires, never the one you hold**. That property is what makes the platform's message safe to show and useless to a prober (`internal/api/identitylane.go`), but on its own the sentence reads as a fact about the route, and an operator comparing it with a role they think they have would conclude the console was lying to them. The request id stays on a denial exactly as on a fault: it is as worth reporting, and more worth quoting to whoever administers the roles. Machine-readably the state is `data-error-status` and `data-denied`, so the e2e reads the status rather than the sentence.

Controls are **not** hidden, and that is D4's decision showing through rather than an omission. The platform has no route that would tell the console what the operator may do — no `me`, no capability manifest, and no role floor at which a role-less authenticated human passes — so the only way to hide a control accurately would be to mirror the platform's claim→role mapping into the console, which is the one thing principle 5 forbids and a drift bug the moment either side changes. Guessing would be worse than the refusal it replaces: a control wrongly hidden is unreportable, while a control that refuses says who to ask. The ask is filed as [platform #403](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/403), which asks for the shape as much as for the route: the reference hands its client a `{permission, status}` manifest rather than a role name, so the authority rules never leave the server, and that property is worth more here than the convenience of a role string. If it lands, hiding becomes possible without any of this having been wrong.

Alongside it the sidebar learns **who is signed in**. A new `/api/auth/session` route answers the browser with the display name and email from the session and nothing else — no role, no subject, no token, `no-store` — and answers `404` on a deployment that runs no identity, so the password-gated and open configurations keep exactly the sidebar they had. The block sits at the foot of the sidebar in the frame the connection status already uses, and carries the only way out: **Sign out** posts to `/api/auth/logout` and then leaves for `/login` **without** a `return_to`, because somebody who signed out deliberately is not asking to be put back where they were. It leaves whatever the POST answers — a console the operator asked to leave, still showing their work in front of whoever is next at the keyboard, is the worse of the two failures, and the login page is where a failed sign-out can be retried.

Review found three, and the first is the one that would have hurt in production. **Not every 403 is a role denial.** The predicate matched on status alone, so a 403 carrying no parseable envelope — which is what an identity proxy or a WAF returns, in HTML — would have been presented to the operator as "your account does not have this role", sending them to an administrator who would find nothing wrong with their roles. Our own GKE staging is IAP-fronted, so this is the likelier 403 there than the one the feature is for. The predicate now requires the platform's own `permission_error` alongside the status, which loses nothing real: `errForbidden` is the only producer of a 403 in the platform's API package and always sets it. Second, a provider that releases a display claim but leaves it **blank** would have put an empty line where the operator's name belongs and suppressed the email behind it, because `""` beats a good email in a `??` chain — a blank claim is now read as no claim, in the same seam that already refuses a blank `sub`. Third, the sign-out request had no bound: a refusal settles, but a connection accepted and then answered by nobody does not, and an unbounded await would have stranded the operator on the console they asked to leave with the button they used now disabled — the exact failure the leave-anyway rule exists to prevent, reached by waiting instead of by erroring. It is now bounded at five seconds and departs in a `finally`.

Verified in Chrome against the same auto-approving OIDC provider, on a console with **no `PLATFORM_API_KEY` in its environment at all**: signing in rendered the block ("Stub Operator" over the account's email), and **Sign out** produced `POST /api/auth/logout` → 200 followed by `/login` with no query — after which `/api/auth/session` reported `signed_in: false` and a BFF call answered `401 authentication_error` / "console sign-in required" carrying the sign-out marker. The reference console's own account block was re-measured the same day rather than recalled: 14px/500 over a 12px muted `Admin · <organization>`. Ours now matches that type scale exactly and diverges only in what the second line says — the email, because the role is unavailable by D4 and the organization does not exist under single-tenant v1 — which is recorded in `docs/design-reference.md`. Surfaces re-shot: none changed; the account block is **not reachable by the fidelity manifest**, which authenticates through the password gate, and putting it in shot needs an identity-mode deployment holding a live session — that is slice 5's boundary, and the manifest gains the surface there rather than gaining a fixture that fakes one.
