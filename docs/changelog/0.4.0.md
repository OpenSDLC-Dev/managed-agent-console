# 0.4.0 — 2026-08-09

The release that gives the console somewhere to be. 0.2.0 made it publishable and 0.3.0 made it honest about what a deployment actually serves; this one runs it. Every push to `main` builds the image, deploys it into a staging cluster in the same namespace as the platform it manages, and refuses to call the rollout green until the pod carrying that image has reached the control plane with the management key and the public address has been observed bouncing an anonymous visitor to `/login` — rolling itself back on any failure after the apply, because a console that failed its own gate has already replaced the one that worked, and leaving it serving on a public IP in front of a full-power management key is the one outcome nobody wants. The console-facing half of that is `GET /api/health`, whose two depths — configuration only, and a real call to the platform — are the only new surface in this release. Everything else here is pipeline.

**Compatibility is measured here, not inherited.** Nothing in this cycle changes a request the console sends — the deep check reuses `GET /v1/agents?limit=1`, the call the agents list already makes — and the pipeline above now puts exactly that request against a real control plane on every merge to `main`. The live tier ran on 2026-08-09 against a `deploy/compose` stack built from [managed-agent-platform](https://github.com/OpenSDLC-Dev/managed-agent-platform)'s `main` at `v0.2.0-12-gdc479fd`: of the four specs that do not drive a model, two pass as written and two fail on an assertion that has become too strict rather than on anything the console does. That platform resolves toolsets at render — its [#343](https://github.com/OpenSDLC-Dev/managed-agent-platform/pull/343) makes `agent_toolset_20260401` and `mcp_toolset` alike echo `configs` and `default_config` with every `enabled` and `permission_policy` concrete, while the stored row keeps the client's own bytes — so a spec comparing an agent's whole `tools` array by equality sees four lines added and none removed. Checked with the console out of the path: a compact `default_config: {"enabled": false}` posted straight to the API comes back with the authored value intact and the platform's defaults spelled out beside it, and after a console save it is still a single entry with `enabled: false` — which is the invariant that spec was written to protect, the explosion into per-tool entries it guards against having not happened. Pinning the superseded render is [issue #66](https://github.com/OpenSDLC-Dev/managed-agent-console/issues/66), not a release blocker. The fifth spec, which drives a real model through the human-in-the-loop path, was not run, so this release does not claim it; the last live tier green as written was 0.3.0's, on 2026-08-08 against the same `main` at `911b6d6`.

- **The delivery job's own credential no longer enters the image build context** (2026-08-08): `google-github-actions/auth` writes the federated credential it mints into the workspace as `gha-creds-*.json`, and the deploy workflow's `docker build .` has that workspace as its context — so the file was landing in the build stage's layer and its cache for the life of the job. The multi-stage build kept it out of the pushed image (only `.next/standalone`, `.next/static` and `public` are copied forward), which is why this is a hardening rather than a leak, but a short-lived credential sitting in a layer nobody meant to put it in is the kind of thing that stops being harmless the first time somebody adds a single-stage variant or exports the cache. `.dockerignore` now excludes it, depth-matched. Two neighbours got the same treatment for the same reason: `.claude/worktrees`, since a parallel-session worktree is an entire second checkout under the repo root that `COPY . .` would otherwise sweep in, and `.env*`, which was anchored to the root and so would not have caught a `.env.local` inside one. The platform repository carries the identical three exclusions — the two pipelines build the same way and share the failure mode.
- **The console deploys itself to a GKE cluster on every push to `main`, and a rollout is not green until it has actually talked to the platform** (2026-08-08): the console had a published image and no deployment — `docker run` in a README is not an environment somebody can open. It now has one: a single staging cluster (`map-staging`, `us-central1-a`) in the same namespace as the platform it manages, so the console reaches the control plane over cluster DNS and **no request carrying the management key crosses a public network** — it never reaches a browser, and it never rides the console's own public address. (That is the runtime guarantee, and it is the narrow one: the deploy job reads the key out of Secret Manager onto a runner to write the Kubernetes Secret in the first place, masked, into a file rather than an argv, shredded on exit.) [.github/workflows/deploy.yml](../../.github/workflows/deploy.yml) builds an amd64 image tagged with the commit sha — amd64 alone is the right answer here, unlike the release workflow's multi-arch build, because the target is one cluster of x86 nodes rather than whoever pulls — pushes it to Artifact Registry, and applies the two objects in [deploy/k8s/](../../deploy/k8s/). **No credential is stored in this repository:** the job mints an OIDC token, Workload Identity Federation exchanges it for an impersonation of a deploy identity that can push images, drive the cluster, and read secrets and nothing else, and both runtime credentials are read from Secret Manager inside the job — `controlplane-api-key`, the same value the platform chart installs as `controlplane.apiKey`, and `console-password`. Rotating either means adding a Secret Manager version, not editing settings on GitHub. A rotation reaches the pod, too: the pod template carries a `console-secrets/checksum` annotation over the two payloads — the same device the platform chart uses — so a `workflow_dispatch` on an unchanged `main` is a new revision rather than a byte-identical apply that reports success, rolls nothing, and leaves the pod on the old credentials. CD deliberately runs no Terraform: the cluster, the registry, the federation pool and the secrets stay human-driven and interactive, and this pipeline owns four verbs — build, push, deploy, smoke. The last one is the point, and it asks two questions from two places. **Can this revision serve?** `kubectl rollout status` proves only that a container starts and answers a probe that touches no network, which a revision with a wrong key passes; so the job runs the deep health check with `kubectl exec` against the pod carrying the image it just pushed, over loopback, logging in with the `CONSOLE_PASSWORD` the container already holds — both variables set, and the platform accepting the key. **Is the public address gated?** From outside, it requires the shallow check to answer 200 (the load balancer routes, the pod serves), the body to report `login_gate: true`, and an anonymous `GET /` to come back 307 to `/login` — that last one being the only one of the three that is evidence, since "a non-empty password existed in Secret Manager at deploy time" is a different claim from "the pod on the internet is gated". It also refuses to deploy at all if `console-password` is empty, because this deployment is published on a bare public IP with **no domain and no TLS yet** (a deliberate, recorded limitation — an Ingress needs a hostname and cert-manager needs a domain, and there is neither), which makes an unset gate an open page in front of a full-power management key rather than the convenience it is on `localhost`. **And a failed gate rolls itself back.** A gate that only reports is not much of a gate: readiness is the shallow check, so a revision the deep check or the public assertion rejects has already replaced the pod that worked, and leaving it serving — possibly ungated, on the internet — is the one outcome nobody wants. Any failure after the apply now runs `kubectl rollout undo` and waits for the previous revision, which is what `helm upgrade --atomic` gives the platform for free and raw manifests do not. It warns about the two things it cannot do: a first deployment has no revision to return to (scale to zero by hand), and a rollback restores the image and not `console-secrets`, since both credentials are `secretKeyRef`s that keep reading the current Secret. Documented end to end in [docs/deploy-gcp.md](../../docs/deploy-gcp.md), including how to roll back by hand — the image tag is the commit sha and is never reused, so every revision the cluster has run is still addressable.
- **A health endpoint, and the login gate no longer hides it** (2026-08-08): `GET /api/health` is the machine-readable answer to "can this revision work", and it has two depths because a probe and a deploy gate want different things — the shallow check reads configuration and touches no network, the deep one (`?deep=1`) also calls the platform with the management key. The readiness probe takes the shallow one on purpose: a probe that failed during a platform outage would remove the console from service exactly when a console that can still render its own error is the more useful thing to have. Liveness takes neither — it takes `/login`, because the shallow check answers 503 for a _configuration_ error and no number of restarts supplies a missing environment variable; pointed there, liveness would turn the readiness failure the rollout is waiting to report into a restart loop that erases it. Wiring the Kubernetes probes surfaced the half that would have made the whole pipeline unusable — `src/proxy.ts`'s matcher covered `/api/health`, so on a gated deployment the endpoint answered 401, which a readiness probe reads as an unhealthy container: the pod would never have become ready, `rollout status` would have timed out, and the smoke gate would have failed every rollout of the one deployment where the gate is **mandatory**. The route is now exempt from the matcher — anchored, along with the two login exemptions beside it, so an exemption names a route and not everything that starts with its name: unanchored, a future `/api/healthz` would have been born outside the gate, silently, on the one deployment where the gate is all that stands in front of a management key. And it is written for the anonymous caller that exemption creates: it names environment variables that are already public in `.env.example` and reports the platform's status code, carrying no URL and no key. **The deep depth gates itself instead.** Exempting the route made `?deep=1` an anonymous lever on a console published at a bare public IP — repeat it and you make the console spend the management key against the control plane on demand — so on a gated console that depth now requires the same session every page does, and answers the login gate's own 401 envelope without it. The deploy gate therefore runs it from inside the pod rather than over the public IP, logging in over loopback with the container's own copy of the password; what crosses the public address is the shallow check and the anonymous request that must be bounced. With `CONSOLE_PASSWORD` unset there is no gate to hold a session against and no console to protect, so the deep depth stays open, exactly as every other route does. Three of the route's twenty tests are `probe:` tests pinning the no-leak invariant: whatever the platform answers — a body echoing the key back, an HTML error page, a rejection whose message quotes the request headers — the serialized health body contains neither the key nor the base URL, and the upstream body is drained rather than left holding a connection.
