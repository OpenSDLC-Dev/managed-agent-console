# 0.2.0 — 2026-08-08

The release that makes releases possible: a published multi-arch image, an automated cut, and a console that states its own version. Nothing about how the console talks to the platform changed, so **compatibility is unchanged from 0.1.0** — the live tier last ran green on 2026-08-04 against a `deploy/compose` stack built from [managed-agent-platform](https://github.com/OpenSDLC-Dev/managed-agent-platform)'s `main` after its `v0.1.0`, and this release touches no platform-facing code.

- **Release management, slice 4 — the console says which version it is** (2026-08-08, plan 05): the sidebar's bottom stack gains a muted `v0.1.0` between the platform-documentation link and the connection status, server-rendered straight from `package.json` — the file release-please bumps — so nothing is kept in sync by hand and no client bundle carries it ([src/components/shell/version.tsx](../../src/components/shell/version.tsx); `resolveJsonModule` was already on). A **recorded divergence** from the reference console, written into [docs/design-reference.md](../../docs/design-reference.md) with its reason: nobody wonders which build of a hosted product they are looking at, but a self-hosted deployment has no other way to tell, and the operator debugging it is the operator who upgrades it. It sits in the same muted register as the connection state rather than as a badge competing with navigation. Two unit tests guard the thing that would actually go wrong — not a wrong string but a **disconnected** one, where a version bump stops reaching the operator's eyes: both read `package.json`, so a hardcoded literal or a second source of truth reddens them. Confirmed able to fail by hardcoding `v0.0.0` and watching the suite go red before restoring. **Fidelity pass: all 28 surfaces re-shot in both themes (56 shots, real Chrome)** — the sidebar is global, so every surface changes — and spot-checked in light and dark against the reference; the login gate, which has no sidebar, is unchanged as expected. 529 unit tests green.
- **Every release PR would have failed CI on a formatting check** (2026-08-07, plan 05): the first release PR release-please opened (`chore(main): release 0.2.0`) went red within 40 seconds, and it would have done so for every release forever. release-please rewrites `.release-please-manifest.json` compactly — `{".":"0.2.0"}` — while prettier, which had formatted the seeded file as `{ ".": "0.2.0" }`, insists on the spaces; `pnpm format:check` is a CI step, so the two tools simply disagreed on a file **no human ever edits**. The file now sits in `.prettierignore` and is committed in release-please's own shape, so the tool that owns it is the only one with an opinion about it. Found the way it should be — by watching the first real release PR rather than by reasoning about one — which is also the evidence that the App credential works: the PR is authored by `opensdlc-console-release[bot]`, carries only `package.json` and the manifest (**`CHANGELOG.md` untouched**, `skip-changelog` doing its job), and **collected CI checks at all**, which a `GITHUB_TOKEN`-opened PR would not have.
- **Release management, slice 3 — the cut is automated, the narrative stays human** (2026-08-07, plan 05): [release-please](https://github.com/googleapis/release-please) now owns version numbers, tags and GitHub Releases — and, by `skip-changelog`, **never touches [CHANGELOG.md](../../CHANGELOG.md)**. That option is the whole reason the automation and this repository's hand-written long-form changelog can coexist: CLAUDE.md says a change's narrative is written once, and a tool that prepends a list of PR titles above 41 KB of prose saying the same things better would have made that false. One step per release stays human because it is the step that requires a human — `pnpm release:prepare X.Y.Z` ([scripts/changelog.mjs](../../scripts/changelog.mjs)) moves everything under `## [Unreleased]` into a dated section, restores the placeholder, repoints the compare-link footer, and bumps README's pinned image tag. The release workflow then **replaces release-please's commit-derived release body with that changelog section**, absolutising its repo-relative links against the tag — a release body resolves `./docs/…` against `/releases/`, not the repository root, so a section copied verbatim 404s on every link it carries. Verified against the real file rather than only fixtures: the generated notes for `0.1.0` are byte-identical across 48 KB to the ones published by hand, and a full `prepare 0.2.0` dry run on the working tree produced exactly the intended diff before being reverted. The transform has **12 unit tests** covering what a bad cut would cost — the one file every change's narrative lives in — including that entries are _moved_ rather than copied, that cutting the same version twice is refused, that an empty `[Unreleased]` is refused rather than shipping a hollow release, and that a malformed file is named rather than corrupted. `release.yml`'s trigger moves from tag push to **`release: published`**: release-please creates releases through the API, which fires no push event, and a bare tag with no release is not a release; `workflow_dispatch` stays as the backfill path. Two facts shaped the credential, both already recorded in the plan and now load-bearing in [.github/workflows/release-please.yml](../../.github/workflows/release-please.yml): a PR opened with `GITHUB_TOKEN` triggers no workflows, so it could never collect the `ci-ok`/`docker` checks `main` requires and `enforce_admins` would leave it unmergeable by anyone; and GitHub's default org policy caps fine-grained PATs at 366 days, so the App (`RELEASE_BOT_APP_ID` + `RELEASE_BOT_PRIVATE_KEY`, `create-github-app-token@v3.2.0`) is what keeps the pipeline from lapsing silently. **PR titles become Conventional Commits**, enforced by a new `pr-title` check and written into CLAUDE.md's iteration workflow — squash merge makes the title the commit subject and release-please reads those subjects, so a prose title is not a style slip but a release that silently does not happen. The check reads the title through an env var rather than interpolating it into the script, since a title is attacker-controlled text on a fork PR. Dependabot gets `commit-message.prefix: chore` for the same reason. [docs/releasing.md](../../docs/releasing.md) is rewritten around the new flow. Review then improved three things. The notes rewrite started out inside the image-publishing job, so **a failed build or trivy gate would have left a published release wearing release-please's placeholder body** — it is now its own job depending on nothing, with the image block appended after it (`publish` needs both, so the two cannot race for the same field). CodeQL flagged the section lookup for building a regex out of an interpolated value; it is a line scan now, which is plainer anyway and provably unchanged — the notes it generates for `0.1.0` are still byte-identical to the pre-refactor output. And the App token now names `permission-contents: write` + `permission-pull-requests: write` explicitly, so a permission granted to the App later cannot silently widen this workflow's token; `permission-issues` was **deliberately not** added despite the review suggesting it, because the action fails when asked for a permission the installation does not hold and this App is installed with two. Cutting the first real release then found two holes in the tooling, both closed here: `release:prepare` bumped README's pinned image tags but not its **status line**, which nothing else would ever correct (release-please touches `package.json` and its manifest and nothing else), so a release would have shipped a README advertising the previous version one paragraph above a pin of the current one; and nothing reminded the maintainer to write the section lead-in carrying the compatibility fact plan decision 9 requires — easy to miss precisely because only the new section becomes the release notes, so the statement sitting in an older section is one this release does not carry. The script now says so on the way out, and [docs/releasing.md](../../docs/releasing.md) makes it a step rather than an implication.
- **Release management, slice 2 — the console becomes pullable** (2026-08-07, plan 05): an operator no longer has to clone this repository to run the console. [.github/workflows/release.yml](../../.github/workflows/release.yml) publishes `ghcr.io/opensdlc-dev/managed-agent-console` on every `v*` tag, tagged `X.Y.Z`, `X.Y`, and `latest`, and README's quickstart is now a `docker run` of that image (the compose service too; `docker build` from a checkout still works and is still what CI gates on every PR). **Nothing reaches the registry that the trivy gate has not already cleared**, which is why the workflow does not use the usual `push-by-digest` multi-arch recipe — that pushes first and scans after. Instead each architecture builds on its own **native** runner (`ubuntu-latest` and `ubuntu-24.04-arm`, free for public repositories; emulating a Next.js build under QEMU is its own argument), is scanned there as a local image under the same HIGH/CRITICAL gate CI uses, and only then pushes `X.Y.Z-amd64` / `X.Y.Z-arm64`; a second job joins the two scanned images into one manifest list with `docker buildx imagetools create`. That path needs **no new third-party action** — buildx ships on the runner and `docker login --password-stdin` handles the registry — so the workflow adds exactly one pinned dependency, the trivy action already in CI. The tag is checked against `package.json` before anything is built, because a version mismatch discovered in a published image is the worst place to discover it. `Dockerfile` gains the OCI labels, `org.opencontainers.image.source` among them — the one GHCR reads to link the package back to this repository — with `VERSION`/`REVISION` as build args so a plain local `docker build` still works. [docs/releasing.md](../../docs/releasing.md) documents the whole flow, including the two things that are easy to rediscover the hard way: a GHCR package is **private on first publish** even when its repository is public (the source label links it without making it anonymously pullable, so the README's `docker run` would fail for every external reader until the package is flipped), and tag-push triggers **do not fire retroactively** — hence `workflow_dispatch` with a tag input, which is how `v0.1.0` gets its image at all, having been tagged one slice before this workflow existed. Recorded there too: that dispatch builds the tag's own tree, so `v0.1.0`'s image carries no OCI labels, and retagging a published release to fix a cosmetic gap would be the worse trade. Review caught two ways the first draft would have lied about what it published, both fixed before merge: it repointed `latest` and `X.Y` unconditionally, so the documented backfill — or two tag builds finishing out of order — would have moved the rolling aliases **backward**, silently downgrading anyone pulling `latest` against README's promise that it follows the newest release; the aliases now move only when the published version really is the newest of all tags, and of its own minor line, with the whole workflow serialized by a concurrency group so competing publishes cannot interleave (logic verified against six orderings including `0.10.0` vs `0.2.0`). And `org.opencontainers.image.revision` was read from `github.sha`, which on the dispatch path is the sha of the ref the run was launched from — the default branch — not the tag actually checked out, so every future backfill would have labelled its image with an unrelated commit; it now comes from `git rev-parse HEAD` after checkout.
