# 0.3.0 — 2026-08-08

The release that makes the console honest about deployments unlike the one it was built against: a surface the platform does not serve now leaves the sidebar instead of sitting there showing the platform's error. That is the first behaviour here that depends on how a platform answers a route it does not have, so the compatibility statement is a measurement rather than an inheritance — **the live tier ran on 2026-08-08 against a `deploy/compose` stack built from [managed-agent-platform](https://github.com/OpenSDLC-Dev/managed-agent-platform)'s `main` after its `v0.2.0`, four of its five specs green**; the fifth, which drives a real model through the human-in-the-loop path, was not run, so this release does not claim it. The new probe was exercised directly against that stack: all six collection routes answer `?limit=1` with 200, and an unregistered route answers 404 `not_found_error` — the two facts the feature reads.

- **Every release cut would have left CHANGELOG.md failing format:check** (2026-08-08): the second real release found the twin of the bug 0.2.0 recorded in `.release-please-manifest.json` — a file no human edits, and two tools disagreeing about it. `cutRelease` wrote the emptied placeholder as `## [Unreleased]\n\nNothing yet.\n`, but the slice it resumes from lands exactly on `## Released`, so the placeholder and the next heading collided and prettier wanted a blank line between them. Every cut from here would have needed a manual `prettier --write` or gone red on `pnpm format:check`, which is a CI step. The existing test asserted `toContain("## [Unreleased]\n\nNothing yet.\n")` — true either way, which is why it passed while the file was wrong; it now names the following heading, so the blank line is what is actually pinned. Found the way the manifest one was: by running a real cut rather than by reasoning about one.
- **A surface this deployment does not serve is now hidden, not rendered as an error** (2026-08-08, issue #33): CLAUDE.md principle 3 has always said that "an unimplemented surface returning 404/501 hides its UI", and nothing implemented it — every non-OK response funnelled into the same red `ErrorState`, so a console pointed at a wire-compatible deployment that lacks, say, skills would sit there showing `no such endpoint: /v1/skills` under a Skills nav item that still invited the click. The issue recorded step 1 as its blocker — decide what the platform actually returns — and the answer, verified against `internal/api/server.go` and a running control plane, ruled out the fix it had sketched: **the platform has no 501 anywhere.** An unregistered route falls through its router's catch-all to the same envelope a missing resource gets — `GET /v1/memory_stores` and `GET /v1/agents/agt_000…` both answer 404 `not_found_error`, identical but for the message — so no status-vs-status helper can separate them, and matching on message text would couple the console to prose the platform never promised. What separates them is the **route**: a collection path carries no id that could be missing, so a 404 on `GET /v1/skills` can only mean the endpoint is absent, and none of the platform's six list handlers has a 404 path to contradict it. That one rule ([src/lib/platform/surfaces.ts](../../src/lib/platform/surfaces.ts)) is the whole mechanism: the shell probes each collection once per session with `limit=1`, drops the nav item and the palette's "Go to" entry for anything answering 404, and the page for such a surface renders `UnavailableSurface` — "Not available on this deployment." — instead of the platform's error text, with its actions and filters gone rather than dangling. Review sharpened three edges. The classifier requires the platform's own `not_found_error` alongside the 404, so an intermediary's bare 404 — a proxy's HTML page, which parses to no envelope and falls back to `api_error` — cannot cost a live surface; it also accepts a plain 501, which the platform never sends but principle 3 names and another wire-compatible endpoint may. And the guard sits on the console layout keyed off the path's first segment, so it stands down a surface's **whole route tree**: a bookmark to `/skills/skill_1` on a deployment without skills no longer opens a detail page over an endpoint that is not there. The list pages keep their own check on their own query's error, which lands a round trip before the shared probe does, so nothing flashes the platform's error on the way to the stand-in. Failure is asymmetric on purpose: **only a confirmed 404 hides anything**, so a 5xx, a dead proxy, or an in-flight probe leaves every surface shown and erroring, because a console that silently loses a feature when the platform hiccups is worse than one that says it is broken. An item route's 404 is untouched and still an error. Covered by a test per surface at both ends (nav item vanishes, page stands in), four e2e tests against a new mock-platform mode that replays the platform's real catch-all response, and `surfaces` is now a probe-ratchet seam — misreading a status here costs a whole feature and no happy-path assertion would notice. Left deliberately out of scope, and worth its own platform issue: a deployment configured **without** object storage or a secrets cipher answers the affected routes with 500 `api_error` ("object storage is not configured on this deployment"), which classifies an operator's choice as an internal fault and offers the console nothing machine-readable — and it degrades per _action_, not per surface, since `GET /v1/files` still serves on such a deployment.
- **The console ships on Next.js 16.3.0, and the lockfile had to be rebuilt to get there** (2026-08-08): a grouped minor/patch bump moves the shipped runtime — Next.js and `@next/env` 16.2.12 → 16.3.0, `@base-ui/react` 1.6.0 → 1.7.0 — plus `eslint-config-next` and `@testing-library/user-event` on the dev side. What is worth recording is not the versions but why the PR sat red: pnpm 11 enforces a **24-hour `minimumReleaseAge` by default**, and the lockfile Dependabot generated referenced two transitive deps published inside that window (`caniuse-lite@1.0.30001809`, `nanoid@3.3.18`, both arriving via Next), so every verify leg failed with `ERR_PNPM_MINIMUM_RELEASE_AGE_VIOLATION` — the repo sets no such policy itself, which is what made the failure look like a broken bump rather than a working supply-chain guard. Re-running after the cooldown would have fixed it untouched; instead the lockfile was rebuilt with `pnpm clean --lockfile` + `pnpm install`, which resolves those two _backwards_ to the newest age-compliant releases (30001807, 3.3.17) and so satisfies the guard rather than evading it. The cost is breadth: a fresh resolution re-resolves the whole tree, so the diff is ~489 lines and carries incidental moves such as `@typescript-eslint/parser` 8.65.0 → 8.66.0, and next week's run will carry the two deliberately-older deps forward again once they have aged. `package.json` was untouched, and all five intended bumps were verified present at their target versions in the regenerated lockfile.
- **The changelog is split by release, so reading it costs one cycle instead of the whole project** (2026-08-08): this file was 61.6 KB, and 76% of it was a single historical section nobody re-reads — the growth is driven by entry _length_, not count (entries here average ~1.8 KB, roughly 18× a typical changelog line, because CLAUDE.md asks each one to carry a change's whole narrative). It now holds the cycle in progress plus a `## Released` index, and each released cycle is a file of its own under [docs/changelog/](../../docs/changelog/), written once by the cut and never edited again — so 0.1.0's 46 KB is one click away rather than in the way of every reader and every agent that opens the file to see what changed this week. `pnpm release:prepare` writes that file instead of a new heading, rewriting the entries' `./…` links to `../../…` as they move two directories down; `release.yml` reads it and absolutises those against the tag, exactly as before. The round trip was verified against the real 0.2.0: regenerated notes differ from the body the workflow actually published by one trailing newline, with all seven of its links resolving. Review caught that the split had quietly dropped a guard — the old lookup found a section _by_ its `## [X.Y.Z] - date` heading, so a mismatch failed, while reading a file by path let any `# …` title be stripped and published under whatever tag `release.yml` asked for; the title must now name the version and carry an ISO date, checked by string compare rather than a regex built from the argument (the CodeQL finding that turned the old lookup into a line scan). Proven inert on the real files: notes for 0.1.0 and 0.2.0 are byte-identical to the pre-guard output. The docs that predate release management were corrected in the same pass — CLAUDE.md no longer describes a docs-only repo with nothing to run, and its command list now names every script CI and the release flow use.
- **The published image is public, and verified to actually run** (2026-08-08, issue #56): the GHCR package was flipped to public, so README's quickstart works as written for the first time — `docker buildx imagetools inspect ghcr.io/opensdlc-dev/managed-agent-console:0.2.0` now returns a `linux/amd64` + `linux/arm64` manifest list from a shell with **no** credentials, at the same `sha256:f020009704057df391e1fdcdd83134829de4f7e44387aa9e237a06fcec97ad7b` digest the release workflow published, where the identical command returned 401 an hour earlier. That flip also let the artifact be checked rather than assumed, which closes plan 05's recorded gap that nothing verified the published image boots: pulled fresh and started with a deliberately dead `PLATFORM_BASE_URL`, `/` redirects to `/login` and the gate renders — the login path working in the shipped image, not only in the suite. All six OCI labels survived the publish, and `org.opencontainers.image.revision` is byte-identical to `git rev-list -n 1 v0.2.0`, which is the `github.sha` → `git rev-parse HEAD` review fix proving itself on a real release: the image points at the commit the tag points at.
